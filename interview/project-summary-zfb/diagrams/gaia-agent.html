Gaia Agent 工程闭环 v2
Gaia Agent · Engineering Closed Loop

在 AWorld 上验证一套 Agent 生产能力闭环

底层用推理优化解决模型服务「跑得快」的问题， 中层用 AmniContext 解决长任务「拿得准信息」的问题， 上层用沙箱挂载和文件系统协作解决「任务真落地」的问题， 最后由 benchmark 打榜反向验证整套方案，并驱动回环调优。

总览闭环：四层能力 + 一条反馈回路

每个节点可点击跳到对应详情；虚线为打榜结果的反哺回路。

01 推理服务层

让 Agent 跑得快

打榜 = 大规模并发跑评测任务，14B 基线吞吐不足，任务时长与 GPU 成本不可控。

方案
  • 部署 Qwen2.5-14B 推理服务（A100 单卡 / H800×8），建立首 token、吞吐、长上下文、batch 维度的评测基线
  • 叠加优化：KV Cache 优化 + FlashAttention + 多步调度
  • 量化选型：GPTQ-INT4 / FP8 / AWQ 对比；投机解码实测验证
指标
+55%~100%A100 单卡 KV Cache：26.61 → 41.42 tok/s
+249%GPTQ-INT4：92.78 tok/s（A100 基线对比）
×21~26bs=256 下 H800 吞吐放大
面试追问点
反直觉结论：投机解码在 14B 上负收益（A100 -7%~23%，8×H800 性能腰斩）——draft 验收开销大于加速收益，需大参数 + 显存吃紧场景才有效；GPTQ-INT4 在多卡 tensor 并行下有权重对齐问题。
02 上下管理层

让信息拿得准

长任务上下文膨胀、污染（Context Rot），长期历史召回不准。

方案 · AmniContext
  • Prompt 模板： 动态引用，统一注入规范
  • 任务状态：基于检查点的持久化，支持会话恢复与子任务上下文构建
  • 三级记忆：工作 / 短期 / 长期记忆 + 事件总线巩固，长期历史召回
  • 多级检索：向量相似度 + BM25 + keyword，Rerank 过滤
  • 四策略对抗四失效：Select 防污染 / Compress 防分心 / Isolate 防混淆 / Write 防冲突
关键设计
  • 子任务只传 result + actions，中间过程落 Memory / Workspace，防上下文爆炸
  • 子 Context 通过 parent 指针向上回溯查找，共享态与私有态分离
面试追问点
为何自研而非 LangGraph / ADK / Manus：面向 MAS 生产环境的长程任务场景（LangGraph 是 state+scratchpad，ADK 是树形 InvocationContext，Manus 是 Plan-Execute+文件卸载），benchmark 驱动召回效果持续优化。
03 沙箱执行层

让任务真落地

Agent 产物与中间文件需要跨容器、跨会话持久化；Multi-Agent 协作缺共享媒介。

方案
  • 建立 Docker ↔ OSS ↔ Agent Workspace 三方挂载映射，实现 Agent 读写文件的持久化
  • 以文件系统作为 Multi-Agent 协作接口：中间文件保存在 Workspace，对话历史落 Memory
踩坑实录
文件找不到：Workspace 路径带 sid 前缀，初版挂载漏掉 sid 导致读路径不命中 → 修正挂载映射；
同步延迟：OSS 挂载默认约 10 分钟同步延迟 → 后台开启快速同步，保证 Agent 读写实时可见。
面试追问点
完整讲一遍读写文件全链路（Agent → Workspace → 挂载层 → OSS）与挂载性能问题。
04 打榜验证层

让能力被证明

开源框架的能力需要客观、可传播的证明，而不是自说自话。

方案
  • Gaia benchmark / xbench 打榜：以公开榜单分数客观度量框架能力
  • 技术报告对外输出：HuggingFace 技术报告（2508.20404）沉淀方法论
闭环价值
  • 打榜 badcase 反哺 01/02：调整 prompt 模板、上下文召回策略、推理配置
  • 榜单分数 → 框架可信度 → 开源影响力，形成工程与传播的双重闭环
面试追问点
xbench 打榜当时遇到了什么问题（环境、评测稳定性、任务时长控制等）。
