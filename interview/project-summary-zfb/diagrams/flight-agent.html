机票 Agent 工程架构与优化闭环

在灵光主对话中集成垂直领域 Agent 的 POC：Agent 连接沙箱、操作真实浏览器实时搜索机票信息。 底层以 MCP Gateway + Sandbox 执行平面获得"能搜索、能点击、能抓取、能验证"的浏览器能力； 中层用 Harness 手段与轨迹数据微调提升稳定性、减少推理轮数； 上层用火焰图埋点、容器预热、推理优化压缩端到端耗时，最终完成 100 并发压测。

整体架构

三层平面：对话入口 → Agent ReAct 循环 → 控制面 / 执行面 / 推理服务

入口层 · 灵光主对话
灵光主对话（Workflow） POC 目标：验证主对话集成垂直领域 Agent 的能力，用户 Query 路由到机票 Agent，结果回流主对话展示
↓
Agent 层 · 机票 Agent（ReAct 循环）
ReAct 循环：模型调用 ⇄ 工具调用 每次轮次 = 一次模型推理 + 一次工具（浏览器操作）执行，直至满足结束条件输出答案
温度参数调优 ReAct 结束条件调优 IP 池接入
模型：GLM-4.5-Air（微调版） 106B-12B MoE；基于批量轨迹采集的 538 条分难度数据，用 Swift 框架在 32×H200 上微调，减少无效推理轮数
↓
执行层 · 控制面 / 沙箱执行面
控制面 · MCP GATEWAY
Agent tool_call→ 鉴权 / trace / method 解析→ Session 粘性路由（容器绑定）→ Forward /mcp
container_id / session_id 绑定 token / cookies / browser auth state session 空闲回收
执行面 · SANDBOX 容器
合并后单一 MCP Server→ agent-browser CLI→ CDP→ Chrome / Chromium
open / snapshot / click / type 航司 · OTA 目标站点 IP 池出口
↓
推理层 · 模型服务
sglang 部署 8×H200，max token 262144
EAGLE 投机解码 num-steps=3 · eagle-topk=1 · num-draft-tokens=4，"猜测 + 验证"机制打破自回归串行瓶颈
产出回传 snapshot / screenshot / trace / 结构化结果，经 Gateway 回流 Agent 上下文

性能分析：火焰图 + 两层埋点

ReAct 本应是"模型调用 + 工具调用"的循环，为定位循环之外的空转耗时，分两层埋点逐层下钻

01 · 稳定性

浏览器方案选型 + Harness 调优

对 kimi-webbridge / agent-browser / Playwright 三方案从架构、控制协议、登录态、风控自然度等维度对比选型，选定 sandbox 内 agent-browser（CDP 路线）。

  • 温度参数调优：降低随机性，稳定搜索行为
  • ReAct 结束条件：避免无效多轮循环
  • IP 池：规避目标站点风控封锁
效果：搜索稳定性提升，作为后续一切优化的基线
02 · 效果

轨迹采集 pipeline → 微调 GLM

设计批量轨迹采集 pipeline，以"轨迹 + 事实依据"双维度评测，为算法侧提供分难度训练数据，配合微调从源头减少推理轮数。

  • 训练数据：538 条，按难易程度分层
  • 训练：Swift 框架，32×H200
  • 模型：GLM-4.5-Air（106B-12B MoE）
效果：推理轮数减少，搜索耗时降低 50%
03 · 性能

火焰图下钻 + 冷启动治理

火焰图 + 两层埋点定位框架异步空转；针对容器冷启动链路做预热与合并，压缩非模型、非工具的额外耗时。

  • 修复状态等待函数固定 5 秒等待
  • 写会话历史改回正确异步语义
  • 容器提前预热；多个 MCP Server 合并为一个，加速启动
效果：对话整体耗时缩短 40%~50%
04 · 推理与并发

sglang + EAGLE 投机解码 · 并发压测

解码阶段 N−1 次 Forward 只能串行、访存瓶颈明显；EAGLE 以"猜测 + 验证"用一次目标模型前向并行验证多个 draft token。

  • 部署：sglang 8×H200，max token 262144
  • EAGLE：num-steps=3 · eagle-topk=1 · num-draft-tokens=4
  • 压测：定位 sandbox 内 MCP Server 未就绪、容器超时等问题后逐项修复
效果：完成投机解码参数验证；压测支持 100 并发

并发问题与对策

压测 100 并发过程中暴露的典型故障与治理手段

问题根因对策
sandbox 拉起后调用即报错 容器起来了，但容器内 MCP Server 尚未就绪，工具调用触发报错 就绪探测 / 启动顺序保障，就绪后再放流量
MCP 工具拉容器超时失败 高并发下服务器容量不足，容器供给排队超时 容量规划 + 容器预热池
启动慢、多 Server 串联拉起 多个 MCP Server 逐个启动，冷启动链路长 多个 MCP Server 合并为一个，缩短启动链路
