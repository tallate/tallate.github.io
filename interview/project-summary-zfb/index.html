  • PROJECT-SUMMARY-ZFB

目标职位

Agent 应用研发工程师

个人总结

具备后端研发背景，近年聚焦 Agent 应用与运行时工程，参与灵光任务 Agent、机票 Agent、支小宝及 AWorld 开源框架建设。具备任务调度、Multi-Agent、Memory、Sandbox、上下文工程、模型推理和可观测性实践，擅长从性能、稳定性、成本和工程落地角度解决复杂问题。此前在钉钉担任文档知识库核心模块 Owner，具备高并发系统和稳定性治理经验。

补充荣誉：钉钉任职期间两次获得 3.75 绩效。

专业技能

  • Agent 工程：Multi-Agent、ReAct、MCP、Memory、Context Engineering、Skill、Sandbox、Agent Runtime、任务调度与可观测性。
  • 大模型工程：Prompt、SGLang、量化、投机解码、轨迹采集与评测，以及模型微调协作。
  • 后端工程：Java、Python、MySQL、Redis、消息队列、Docker、Nginx、Sentinel、OSS。
  • 工程治理：性能分析、高并发、稳定性、成本优化、监控告警与故障排查。

工作经历

负责 Agent 应用与运行时工程研发，参与灵光任务 Agent、机票 Agent、支小宝及蚂蚁 AWorld 开源框架建设，覆盖产物生成、任务调度、Memory、Sandbox、上下文工程、CLI Harness 和推理优化等方向。通过限流、优先级调度、重试和 Watchdog 等机制，显著提升长任务执行成功率；通过模型微调与框架性能优化，将机票搜索耗时降低 50%，并完成 100 并发基准压测；作为 AWorld CLI 核心贡献者参与开源建设及社区大会技术演示。

灵光任务Agent 2026.02-至今

项目介绍：面向主对话难以承载的长耗时复杂任务，建设支持定时任务、产物生成的后台任务 Agent，并兼容自研 Runtime 与 OpenClaw Runtime。
职责：

  • 产物生成：负责端到端文件产物生成及预览，集成多种生成 Skill 并优化效果；引入 Spec 驱动的 Multi-Agent Coding 流程，约束前后端 Agent 协同，提升代码产物可用性和约 10% 的生成效率。
  • Runtime 兼容与演进：参与自研 Runtime 和 OpenClaw Runtime 的接入与适配，抽象任务状态、工具调用、文件产物、Skill管理等共性能力，降低业务层对底层执行环境的依赖。
  • 任务调度与稳定性：设计 Redis 限流、优先级调度、随机偏移、重试和 Watchdog 机制，将任务成功率提升至 95% 以上。
  • Memory 与可观测性：设计长期记忆的增量抽取与检索方案，建立任务调度、端到端链路、首 Token、异常 Trace 分析和定时巡检能力。

面试模拟重点：

  • 如何优化产物生成效率：先统计各阶段耗时和剩余预算，在接近超时时插入 user message 约束 Agent 收尾；将上下文压缩阈值从 70% 调整至 50%，提前压缩以减少末段集中处理耗时；为 PublishFlashApp 工具补充报错堆栈，加快 Coding Agent 定位和修复代码。
  • 如何提升产物可用性：在编码前由 Agent 生成 spec.md，再由 Backend Agent 和 Frontend Agent 按统一规格实现；服务化闪应用在交付前调用服务端接口完成验证。
  • 压缩阈值调低有什么代价：压缩更频繁，可能增加模型调用成本并丢失细节；通过 spec.md、Workspace 产物和结构化 Todo 保存关键约束，降低上下文压缩风险。
  • Memory 如何提升抽取性能：对 Transcript 分段抽取并记录抽取位点，仅处理新增内容；重新发起会话时根据位点识别未抽取区间。
  • 为什么单容器并发过高会降低任务成功率：长任务占用会话和运行资源的时间较长，如果任务结束后资源没有及时释放，资源会持续累积，引起容器内资源争抢、任务排队和执行超时，并进一步触发重试和 Watchdog。通过清理无效会话与任务资源、限制单容器并发、调优队列和完善任务结束后的资源释放，降低资源争抢并提升任务成功率。
  • ⭐ “生成效率提升约 10%”的具体口径是什么：端到端耗时、单位时间完成数、一次生成成功率，还是人工返工时间？需要统一基线、样本量和统计周期。
  • ⭐ “任务成功率提升至 95% 以上”如何定义成功？需要准备统计范围、样本量、失败类型分布，以及限流、重试、Watchdog 各自贡献了多少。
  • ⭐ 具体清理了哪些单容器资源，分别在什么生命周期节点触发？需要确认是否包括会话状态、临时文件、Sandbox、连接、缓存或执行进程，避免面试时泛化描述。
  • ⭐ 自研 Runtime 与 OpenClaw Runtime 的统一接口、差异点和切换边界是什么？至少准备任务状态、工具协议、文件产物、Sandbox 生命周期四个方面。
  • ⭐ Memory 如何降低抽取成本，为什么没有直接采用 OpenViking？需要准备数据规模、增量策略、检索评测和自研/开源方案对比。
  • ⭐ Agent 可观测性如何设计？需要能说明 Trace/Span 模型、模型与工具耗时、Token/成本、状态迁移、错误分类、告警和单任务回放。

逻辑链：

灵光任务 Agent 将主对话中受时长、上下文和资源限制的复杂需求转成可调度、可恢复、可评测的后台任务：主对话负责识别和委派；Scheduler、Dispatcher 与 TaskRunner 通过队列、优先级、限流、重试和 Watchdog 管理 Job/Plan 生命周期；Goal 控制线程级持续执行，Plan/Todo 表达步骤和进度；任务 Agent 再通过 Multi-Agent 将 Coding、File/PPT 等工作委派给专业 Agent。运行过程中，Session Checkpoint 与 Context Snapshot 恢复模型上下文，Memory 保存跨 Session 信息，Skill/Plugin 与 Sandbox 提供能力和隔离环境，Workspace 保存真实中间成果。最后由 Artifact 完成交付，Reward、Verify、稳定性和 TTFT 观测形成反馈闭环。

需要注意：当前 Checkpoint 是 Session/Context 恢复机制，不是步骤级长程任务状态；默认未启用 TaskGraph，失败后由调度器重新触发，Agent 根据恢复后的上下文、Todo 和 Workspace 自检继续执行。

AWorld CLI 2026.01-2026.03

项目介绍：面向蚂蚁开源 Agent 框架 AWorld 建设 CLI Harness，以命令行形态提供代码编辑、终端、Skill、Subagent、上下文管理和多模态能力。
职责：

  • 设计多层级 Skill 管理和自定义 Subagent，实现基于文件的 Memory 存储与压缩、终端流式输出及 Token Cost 统计，提升长任务的上下文管理和执行体验。
  • 优化代码编辑和回滚工具，使用 Tree-sitter 构建 AST 分析与代码搜索能力，解决大代码库搜索卡死和代码替换不准问题。
  • 接入多模态模型协议并支持视频理解与按剧本生成视频；通过优化模型网关 Keepalive，提升大段代码和长响应输出的稳定性。
  • 作为 AWorld CLI 核心贡献者参加南京魔搭社区大会，负责 Agent Harness、代码工具、Skill、Subagent 和上下文管理等能力的现场演示与技术讲解。

公开证据：

  • AWorld 官方开源仓库
  • AWorld CLI 源码
  • AWorld 技术报告：AWorld: Orchestrating the Training Recipe for Agentic AI

面试模拟重点：

  • AWorld、Agent Runtime 和 CLI Harness 的关系是什么：AWorld 提供底层运行时，CLI 将上下文、工具、Subagent 和交互能力组装为可直接使用的开发者产品。
  • 为什么使用文件保存 Memory：便于人和 Agent 共同读写、版本管理、按需加载和跨 Session 恢复，同时需要处理文件膨胀、检索效率和敏感信息隔离问题。
  • 为什么使用 Tree-sitter：相较纯文本搜索，AST 能识别语言结构和符号边界，适合定义、引用和局部代码块检索；同时保留文本搜索作为未知语言和非代码文件的兜底。
  • 代码替换失败如何处理：替换前校验目标片段唯一性和文件版本，执行后检查结果；失败时缩小编辑范围或改用结构化定位，并保留快照支持回滚。
  • ⭐ CAST 系统的三层索引分别是什么、如何构建、如何增量更新？需要从实际实现中整理完整调用链。
  • ⭐ AST 搜索、代码编辑和 Keepalive 优化分别提升了多少？至少补充搜索耗时、卡死率、编辑成功率或长输出失败率中的一项指标。
  • ⭐ 文件 Memory 在什么时候压缩、压缩哪些内容、如何防止关键信息丢失？需要准备触发阈值、摘要格式和恢复机制。
  • ⭐ 视频理解为什么能够降低 Token Usage？需要说明帧采样、内容压缩、模型协议适配和优化前后口径。

逻辑链：

AWorld CLI 这个项目，本质上是把 AWorld 从底层 Agent Runtime 产品化为开箱即用的 Agent Harness：底层通过 AmniContext 上下文治理（基于文件的 memory 存储与压缩、多层级 skill 管理、自定义 subagent）解决长程任务的上下文腐烂问题；中层通过 CAST / tree-sitter 三层索引与代码编辑工具（代码替换不准修复、代码回滚、AST 搜索提速避免搜索卡死）解决大代码库理解与编辑的可靠性问题；上层通过 CLI 形态（终端流式输出、token cost 统计、多模态模型协议集成）把能力低成本交付并支持管道组合；最后通过南京魔搭大会现场演示验证开源影响力与落地效果。

机票Agent 2025.11-2025.12

项目介绍：探索灵光主对话集成垂直领域 Agent 的工程方案，通过 Sandbox 中的浏览器 Agent 实时搜索、交互和验证机票信息。
职责：

  • 设计基于 Sandbox 的浏览器 Agent，完成浏览器方案选型和稳定性测试，通过调整温度参数、ReAct 结束条件及接入 IP 池提升实时搜索稳定性。
  • 设计批量轨迹采集与事实依据评测 Pipeline，配合算法团队使用 538 条分难度轨迹数据微调 GLM-4.5-Air，减少推理轮数并将搜索耗时降低 50%。
  • 使用火焰图和分层埋点定位框架异步空转，结合容器预热、MCP Server 合并和容量治理，将对话整体耗时缩短 40%～50%，并完成 100 并发基准压测。

面试模拟重点：

  • 如何分析性能：将 ReAct 拆为模型调用和工具调用循环；第一层记录每轮模型、工具起止时间，第二层记录模型 Client 和 MCP Client 的起止时间，用总耗时减去有效调用耗时定位框架空转，最终发现固定 5 秒状态等待及会话历史异步转同步等额外开销。
  • 并发阶段遇到了什么问题：Sandbox 已启动但容器内 MCP Server 尚未就绪；服务器容量不足导致拉起容器超时。通过健康检查、容器预热、容量治理及合并多个 MCP Server 缩短启动链路。
  • 浏览器方案如何选型：从控制协议、页面理解、登录态、风控自然度、Sandbox 集成成本和可观测性等维度，对比 Playwright、Agent Browser 等方案。
  • 模型与部署：GLM-4.5-Air MoE 模型，训练侧使用 Swift 和 32×H200，数据集包含 538 条分难度轨迹；推理侧使用 SGLang 和 8×H200，最大上下文 262144，并使用 EAGLE 投机解码（num-steps=3、eagle-topk=1、num-draft-tokens=4）。
  • ⭐ 100 并发压测使用什么模型和资源配置？需要准备 QPS、P95/P99、错误率、持续时间，以及“并发会话”还是“并发请求”的准确定义。
  • ⭐ 搜索耗时降低 50% 与整体耗时降低 40%～50%是否来自同一批测试？需要区分推理轮数优化、框架空转优化和容器冷启动优化的贡献。
  • ⭐ 轨迹评测如何判断答案正确？需要说明事实依据、价格时效、航班一致性、任务成功率和人工/自动评测规则。
  • ⭐ 538 条数据如何划分训练集和验证集，如何避免过拟合？你在数据、训练、部署和评测中的个人责任边界是什么？
  • ⭐ EAGLE 的实际接受率、输出速度提升和质量变化是多少？目前只有参数，没有收益数据。

逻辑链：

机票 Agent 这个项目，本质上是验证「主对话集成垂直领域 Agent」的完整工程闭环：底层通过 MCP Gateway + sandbox 执行平面（agent-browser CLI 经 CDP 控制真实浏览器）解决实时信息获取能力，让 Agent 从”读网页”升级到”能搜索、能点击、能抓取、能验证结果”；中层通过 Harness 手段（温度参数、ReAct 结束条件、ip 池）解决搜索稳定性问题，再通过批量轨迹采集 pipeline + 轨迹和事实依据评测驱动算法侧微调 GLM-4.5-Air（538 条分难度数据、Swift 框架）减少推理轮数；上层通过火焰图 + 两层埋点定位框架异步空转（状态等待固定 5 秒、异步转同步写会话历史），配合容器预热、多 MCP Server 合并一个等手段压缩冷启动与空转开销；推理侧用 sglang + EAGLE 投机解码（num-steps=3 / eagle-topk=1 / num-draft-tokens=4）压低解码延迟，最终对话整体耗时缩短 40%-50%、搜索耗时降低 50%，完成 100 并发压测。

Gaia Agent 2025.03-2025.10

项目介绍：基于 AWorld 构建 Gaia Agent、推理服务和 Sandbox 执行环境，面向 GAIA Benchmark 验证复杂推理与工具使用能力，并沉淀公开实现和专项技术报告。
职责：

  • 负责打榜推理服务部署与性能评测，调研并验证量化、投机解码等方案，优化模型服务吞吐和响应速度。
  • 为 Agent 框架设计 Prompt 模板和上下文能力，实现长期历史召回，并通过 Benchmark 迭代上下文召回效果。
  • 设计 Sandbox 文件挂载能力，建立 Docker、OSS 与 Agent Workspace 的路径映射，实现 Agent 文件读写和产物持久化。

支小宝 2024.09-2025.02

项目介绍：面向支付宝生活服务场景建设多 Agent 对话能力，通过意图识别和领域 Agent 完成天气、账单、点咖啡等任务，并提供跨轮上下文连续性和内容安全治理。
职责：

  • 设计事件驱动的 Memory 抽取与上下文注入系统，从对话历史中抽取已返回的视频链接等业务特征，供领域 Agent 感知历史结果并减少多轮重复推荐。
  • 对接安全 Agent，定义拦截、提示和异步撤回策略，在流式输出性能与违规内容暴露窗口之间进行权衡。

面试模拟重点：

  • 为什么需要 Memory：Base Agent 无法获取主对话完整历史，搜索结果中的视频可能在多轮对话中重复出现；通过异步抽取已展示的视频链接并在后续请求中注入，使领域 Agent 感知历史结果。
  • JSON 抽取不稳定怎么处理：在 Prompt 中增加多组 Few-shot，约束字段类型和输出格式；工程侧还应增加 Schema 校验、解析失败重试和降级策略。
  • 异步撤回有什么风险：流式响应每若干 Chunk 检查一次，异步方式减少首 Token 和输出延迟，但违规内容可能在撤回前已被用户看到或截图，需要通过更小检测窗口、前置高风险分类和分级策略降低风险。
  • ⭐ Memory 抽取和上下文注入后，重复推荐率或用户体验指标改善多少？目前缺少结果数据。
  • ⭐ Memory 的事件来源、存储模型、幂等机制和查询链路是什么？需要能画出写入、加工、召回、注入的完整时序。
  • ⭐ 安全 Agent 的误杀率、漏检率和响应耗时是多少？同步检查与异步撤回的适用边界是什么？
  • ⭐ Few-shot 之外是否使用 JSON Schema、约束解码或自动修复？需要解释当时为何选择 Prompt 方案及其局限。

逻辑链：

支小宝这个项目，本质上是为多 Agent 生活服务对话建立一套“上下文连续性 + Prompt 治理 + 安全治理”的工程闭环：主对话和领域 Agent 在执行过程中将 Session、Dialog、Agent 结果等信息增量写入 Memory；事件驱动的实时/旁路 Pipeline 与离线任务进一步完成对话总结、事实和特征抽取，并写入 Lindorm 等存储与检索系统；查询侧通过完整 Memory 或按元数据定义的 MemoryView 召回历史上下文，再由 Prompt Select 将上下文参数注入统一管理的 Prompt，供模型直出、RAG、Policy 和后续 Memory 加工消费。以视频搜索为例，这条链路让拿不到完整主对话历史的 Base Agent 感知已返回的视频结果，避免多轮重复推荐；同时通过 Few-shot 提升 JSON 结构化抽取的稳定性。安全侧以流式分段检测和异步撤回作为旁路，在响应性能与违规内容暴露窗口之间做权衡，最终形成“对话执行 → 记忆写入 → 事件加工 → 检索注入 → 业务消费与安全反馈”的闭环。

钉钉文档搜索与推荐 2021-2022

项目介绍：负责钉钉文档搜索组件和常用文件推荐能力建设，解决搜索索引数据倾斜、文档快照同步、推荐关系建模和异步写入压力问题。
职责：

  • 为文档搜索设计二级分片键，解决长期数据倾斜；建设文档快照增量与离线全量同步链路，将数据稳定接入 HA3 搜索引擎。
  • 设计用户、文件和空间的图关系模型，通过关系检索生成常用文件推荐列表；参与粗排、精排和点击埋点建设，持续优化首屏推荐效果。
  • 通过消息队列消费限流、无效数据过滤、重复事件聚合和定时清理降低图库写入压力，并通过读写分离提升推荐查询稳定性。

面试模拟重点：

  • 搜索链路如何讲：文档变更事件进入消息队列，经过过滤、聚合和限流后同步到搜索索引与图关系存储；查询侧先由 HA3 召回，再结合图关系推荐、粗排和精排生成首屏结果，最后通过点击埋点形成反馈。
  • 为什么需要二级分片键：单一分片键长期容易形成热点或数据倾斜；二级分片需要同时考虑查询路由、扩容迁移、全量重建和增量一致性，不能只解决写入均衡。
  • 图库如何降低数据压力：过滤不支持搜索的快捷方式、单聊文件等无效数据，约减少 50% 写入；同一文档短时间连续编辑会产生重复事件，因此按文档维度聚合后再写入。
  • 搜索排序规则：根据用户行为类型设置基础权重，结合操作次数和最近行为的时间衰减计算得分；规则排序可解释、上线快，但仍需线上实验验证并逐步引入更实时的特征。
  • ⭐ 搜索效果指标究竟是召回率、准确率、首屏点击率还是 NDCG？备份材料中的“提升 5%～10%”口径不清，因此暂不放入职责，投递前需要确认实验指标、基线和样本范围。
  • ⭐ 为什么选择 GDB/iGraph，图模型相较 MySQL 或搜索引擎有什么优势？迁移时采用双写、回放还是离线重建，如何校验一致性？
  • ⭐ Kafka/消息队列使用什么分区键，如何处理顺序性、重复消费、限流和积压？需要结合真实文档事件链路回答。
  • ⭐ HA3 全量与增量同步如何避免丢数据或旧数据覆盖新数据？需要准备版本号、时间戳、索引切换和数据校验机制。
  • ⭐ 搜索项目的准确起止月份需要确认；当前仅按已有经历保守写为 2021-2022。

逻辑链：

这段项目按“数据生产 → 异步治理 → 索引与关系建模 → 召回排序 → 行为反馈”来讲：文档创建、编辑和访问行为先转成事件；消息队列负责解耦，过滤无效数据、聚合重复事件并限制下游写入速率；文档快照通过增量与离线全量链路进入 HA3，用户、文件和空间关系进入图库；查询时由搜索索引完成文本召回，再结合关系推荐和粗排、精排生成首屏结果；最后用点击埋点观察效果并迭代规则。二级分片解决数据倾斜，读写分离和定时清理保障链路在数据增长后的稳定性。

钉钉文档知识库与稳定性治理 2022-2024.08

项目介绍：围绕钉钉文档知识库权限和全网公开能力建设，在业务规模扩大后持续治理权限一致性、高并发访问、容量成本和系统稳定性问题。
职责：

  • 作为知识库核心模块 Owner 推动项目交付，基于 RBAC 管理目录树资源权限，通过限流、读扩散、冗余数据和定时对账解决大部门高并发赋权与最终一致性问题。
  • 参与设计全网公开访客 UID 池和文档快照发布能力，通过压测和缓存优化将打开链路提升至 1000 QPS，支撑约 3 万 DAU、4.5 万 PV 的运营活动。
  • 通过监控埋点定位热点链路，在请求、元数据查询和鉴权链路增加分层缓存，使 MySQL 核心负载降低约 40%；治理 Redis 大 Key 并调整内存淘汰配置，使 Redis 内存使用降低约 20%。
  • 主导核心场景压测与有损演练，设计数据库切备快速恢复和异步消息限流削峰方案；配置 Sentinel 限流、改造 Nginx 灰度发布，并定位解决 Upstream 重复失败导致的 502 问题。

面试模拟重点：

  • 高并发权限写入为什么使用读扩散：对超大部门或群体，如果写时为每个成员展开权限，会产生大量写放大和脏数据；改为查询时结合组织关系计算，并用冗余数据和缓存控制读取成本。
  • 数据扩散产生脏数据如何解决：异步链路失败或成员关系变化会导致权限副本不一致，通过幂等消费、失败重试、定时对账和差异修复保证最终一致性。
  • 访客 UID 池如何工作：预生成有限访客身份，通过哈希桶定位分片、队列完成租借和回收，避免每次访问同步创建账号；需要处理幂等、耗尽、重复分配和回收失败。
  • 稳定性治理如何分层：事前通过容量评估、压测、限流和预案降低风险；事中通过监控告警、降级和切备止损；事后通过复盘、对账和演练验证改进。
  • 为什么在请求、元数据和鉴权链路分层加缓存：不同数据的更新频率、一致性要求和热点模式不同，需要分别设计 Key、TTL、失效通知和降级逻辑。
  • Nginx 502 如何排查：从客户端、Nginx、Upstream 服务和网络四层核对错误日志、连接状态、超时与重试行为，最终定位重复失败节点未及时摘除的问题。
  • ⭐ MySQL“核心负载降低 40%”具体指 CPU、查询量、连接数还是实例水位？Redis“降低 20%”是已用内存还是峰值水位？简历前必须统一指标定义。
  • ⭐ Redis 大 Key 如何发现、删除和预防？需要准备扫描方式、业务访问模式、渐进式删除、过期/淘汰配置和拆分方案。
  • ⭐ 切备方案的 RTO/RPO、切换条件和数据一致性风险是什么？“有效提升可用性”需要补充可验证结果。
  • ⭐ Sentinel 限流采用什么规则，阈值如何确定，触发后如何降级？需要说明活动流量估算和压测过程。
  • ⭐ 项目的准确起始月份需要确认；当前依据已有资料保守写为 2022 年开始。

逻辑链：

这段经历按“业务能力建设 → 规模问题暴露 → 权限与容量治理 → 稳定性体系化”来讲：先用 RBAC 和资源视图支撑知识库目录树权限，用访客 UID 池和文档快照承接公开访问；当部门规模和运营流量增长后，权限写扩散、异步数据不一致、热点访问和缓存成本逐渐成为瓶颈；随后通过读扩散、冗余视图、消息限流、定时对账和分层缓存治理一致性与容量；最后把单点优化沉淀为稳定性体系，形成事前压测与限流、事中监控降级与切备、事后对账演练和复盘的闭环。
